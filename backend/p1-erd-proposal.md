# P1 ERD 합의 초안

이 문서는 [현 ERD](../docs/ERD.md)의 5개 테이블을 [PRD v1.1](../docs/GigSplitter-PRD-v1.1.md)과 [백엔드 계획의 P1](./plan-backend.md#p1--erd-기반-운영-저장)에 맞추기 위한 논리 스키마 제안이다. 원본 ERD는 v1.0의 스키마이며, 이 문서는 배포 DB·인증·보관 정책을 확정하거나 DDL, 마이그레이션, 운영 기능을 추가하지 않는다.

## 1. 현 ERD와 P1 후보 매핑

| 현 테이블 | P1 저장 후보 및 변경점 | 근거 |
| --- | --- | --- |
| `users` | 안정적인 `id`, `display_name`, `created_at` 유지. 이메일은 인증 수단이 사용하는 경우 정규화 후 유일; 비밀번호 방식이면 해시만 저장. 방장·공구원은 전역 `role`이 아닌 공구 소유·참여 관계로 판정. 외부 인증이면 `(provider, subject)`를 유일하게 내부 `user_id`에 매핑. | ERD `users`; PRD §2·§7 |
| `product_analysis` | 인증 소유자의 확인 입력을 스냅샷으로 저장. `UPLOAD/PRESET`·`GEMINI/FALLBACK` 조합만 쓰는 대신 입력 경로·판독 여부·비교 출처 분리. 신규 `comparison_baseline`은 분석당 0~1행, 미확인 비교 허용. | ERD `product_analysis`·계산 규칙; PRD F-14·§4·§6·§7 |
| `group_buy` | `host_id`, `analysis_id`, 방장 포함 `headcount` 2~4, 공개 장소·모집 `title/body` 유지. 초안, 실제 마감·수령 일정, 상태, 확정 버전 포인터 추가. 신규 `group_buy_event`에 상태 변경·제외·취소 사유 및 조치, `group_share_link`에 공개 범위·버전 귀속 기록. | ERD `group_buy`·상태 규칙; PRD F-07·F-14~F-16·F-18~F-19·§5 |
| `settlement_share` | 현재 좌석은 `group_seat`, 신청·승인은 `group_participation`으로 분리. 확정값은 신규 `settlement_version`·`settlement_line`·`settlement_confirmation`, 운영 이력은 `cash_event`·`receipt_event`에 기록. 가변 자리의 `qty/amount`를 확정값으로 쓰지 않는다. | ERD `settlement_share`·동시 참여·계산 규칙; PRD F-07·F-15~F-19·§4~§6 |
| `saving_record` | 키를 `(user_id, analysis_id)`에서 `(group_buy_id, user_id)`로 변경. 현재 집계값, 근거 버전 및 실제 부담금을 기록. 같은 분석에서 서로 다른 완료 공구는 각각 집계한다. | ERD `saving_record`·방장 기준 산식; PRD F-08·§5·§8·§9 |

## 2. 익명 P0와 인증 P1: 입력·출처·비교

- **P0 비저장 유지.** [`server.js`](./src/server.js)의 `GET /api/presets`, `POST /api/products/extract`, `POST /api/analyses`는 로그인·DB 없이 요청에 응답하며, 서버에 분석 ID·이미지·사용자 기록을 남기지 않는다. P1 저장은 로그인한 사용자가 초안을 만들 때 확인 입력을 새로 제출하는 별도 경로다. P0 계산 응답·판독 결과·프리셋 사용만으로 P1 행을 만들지 않는다.
- **초안과 확정 입력 분리.** `group_buy`는 `id, host_id, analysis_id, headcount, status, revision, created_at, updated_at, published_at, closed_at, completed_at, cancelled_at`, 공개 수령 거점, 신청 마감 시각·신청 방법, 수령 후보 및 확정 일시(시각은 타임존 명시), 모집 제목·본문, `pending_version_no/current_version_no`를 갖는다. `DRAFT`에서는 일부 운영 필드와 `analysis_id`가 비어도 되며, 허용 필드만 담은 `draft_input`으로 미완성 폼을 복원한다. 자동 저장은 소유자와 `revision`을 확인해 오래된 요청이 덮어쓰지 못하게 한다. 게시 트랜잭션에서 검증된 분석·좌석·모집 문구를 연결하고 작업용 `draft_input`을 제거한다. 미게시 초안만 삭제 가능; 게시 이후엔 취소·이력으로 남긴다. 장소 미정은 `NULL`이며 로비 기본값을 강제로 넣지 않는다. P0의 마감 문자열은 P1의 구조화된 마감으로 명시 확인하며 임의로 파싱하지 않는다.
- **확인 입력이 기준.** `product_analysis`는 `id, user_id, created_at, confirmed_at`, `short_name/full_title`, `bulk_qty/unit_name/allocation_step/uniform_units`, 확인한 옵션·포장수·팩당 수량·개별 순량과 단위(알 때만), 대용량 비교 규격, 선택적인 `annual_purchase_count`를 저장한다. 금액 원천은 `product_amount, shipping_fee, discount_amount, includes_shipping, includes_discount, is_estimate`; `totalAmount`는 재계산한다. 입력이 바뀌면 새 스냅샷을 만들고 공구의 편집용 `analysis_id`만 가리키게 한다. 연결하는 분석은 해당 방장 소유여야 한다.
- **출처와 판독을 혼동하지 않는다.** `input_origin = MANUAL | CAPTURE | SAMPLE`, `extraction_method = NONE | GEMINI`, 해당하는 경우 `extraction_model`, 포착·확인 시각, `preset_id/preset_revision`, 확인 주체를 기록한다. 익명 판독에서 건너온 출처는 서버가 검증한 판독이라고 간주하지 않는다. [`gemini.js`](./src/gemini.js)의 옵션·상품 가격 후보와 `unresolvedFields`는 확인 화면의 보조값이며 혼합 장바구니 총액·판독 원문을 확정 가격으로 저장하지 않는다. 원본·원시 응답 저장 없이 확인된 필드로 다시 연다. 캡처 링크는 공개 필드가 아니며, 별도 증빙 보관이 승인될 경우에만 비공개 저장소 참조와 만료·삭제 정책을 둔다(PRD §7).
- **비교 보류는 정상.** `comparison_baseline.analysis_id`는 PK/FK. `quantity, unit_name, price`, 호환 키·공통 단위·정확한 개별 환산량, `source_kind = USER_INPUT | SAMPLE`, 선택적 `reference_kind = LINK | SCREENSHOT`, 출처 참조/설명, `checked_on`, 확인 주체/시각 및 샘플 ID·개정 정보를 저장한다. 분석은 `comparison_status = READY | PENDING`, `comparison_pending_reason`을 가질 수 있다. 보류 시 검증된 부분 입력만 남기며 가격 미입력·규격 미확인/불일치·출처 미확인·샘플 불일치를 구분하고 배분은 허용한다. `READY`는 양의 기준가·수량, 호환 규격, 확인된 출처가 모두 필요하며 `SAMPLE`이면 등록값과 대조한다. 이 구분은 [`analysis.js`](./src/analysis.js)의 `compare`와 [`presets.js`](./src/presets.js)의 시연 데이터에 대응한다. 시연 기준가는 운영 절약 기록에 쓰지 않는다. 샘플에서 시작한 초안도 실제 상품·가격을 확인해야 게시하며, 실제 비교가 없으면 비교 보류로 남긴다(제안).
- **공통 계산·범위.** `validateProduct`의 80자/200자 상품명, `validateOptions`의 장소/마감/신청 방법 100/100/150자, JS 안전 정수 범위와 저장 API를 일치시킨다(현 ERD의 이름 60자 및 DB `INT`와 차이). `shippingFee`/`discountAmount`는 이미 포함되었으면 다시 반영하지 않는다. 수량·배분 최소 단위는 양의 정수, 전체 수량은 최소 단위의 배수, `uniformUnits = true`일 때만 배분한다. 각자 최소 한 단위가 있어야 한다. 배송·할인·결제 총액은 음수가 아닌 원화 정수(P0는 0원 허용), 연간 횟수는 선택적 양의 정수. 환산량은 부동소수 열이 아닌 정확한 정수(예: 길이 mm)로 저장하고 중간 곱셈·합계는 안전 정수 범위를 초과해도 정확하게 계산한다. 배분 단위와 비교 단위는 독립이며 단가·절감률은 별도 저장하지 않는다. `settle`과 같이 수량은 균등 배분 후 방장에게 나머지를, 부담금은 수량 비례 내림 후 소수 잔여가 큰 순으로 1원씩 배정한다. 동률이면 방장, 이후 참여 확정 순이다. 표시 단계 전에는 절감액을 반올림하지 않으며 음수도 보존한다.

## 3. 신청·승인·좌석 원자성 (F-15, §2·§5·§8)

| 후보 | 필드·키·규칙 |
| --- | --- |
| `group_seat` | PK `(group_buy_id, seat_no)`, 현재 `user_id`·`assigned_at`은 빈 자리에만 `NULL`. 비어 있지 않은 `(group_buy_id, user_id)` 유일(빈 자리는 여러 개 허용). 게시 시 정확히 `headcount`개, `0 ≤ seat_no < headcount`; 0번은 반드시 `host_id`로 열고 비우거나 양도하지 않는다. 나머지 점유는 같은 공구의 승인된 참여자만 참조한다. |
| `group_participation` | PK `(group_buy_id, user_id)`로 한 공구의 같은 계정 신청은 한 행. `invite_link_id`, `alias`, `status = PENDING | APPROVED | WITHDRAWN | REJECTED | EXCLUDED`, `requested_at, decided_at, decided_by, approval_seq`, 변경 사유를 저장. 방장은 별도 신청하지 않는다. 철회 후 재신청을 허용하는 경우 기존 행을 명시적으로 `PENDING`으로 복귀시키고 이력을 추가한다. 승인 순번은 한 공구에서 중복 없이 새로 배정하고 좌석 번호와 혼용하지 않는다. |
| `group_buy_event` | 단조 증가 `event_no`와 `(group_buy_id, event_no)` 유일. 행위자·대상 참여자·요청 키·시각·변경 구분·사유 및 조치·관련 정산 버전 기록. 동일 명령 키는 기존 결과 재사용; 다른 내용의 키 재사용은 거부한다. 공개 응답에 원문을 노출하지 않는다. |

- 방장만 자기 공구 게시·수정·승인·제외·정산 확정·입금/수령 확인. 참여자는 유효한 공구별 초대와 인증·본인확인 후 자기 신청/철회, 자기 정산 재확인·송금 표시만 가능하다. 유효 토큰만으로 참여자 또는 방장 권한을 주지 않는다. 모든 조회·쓰기는 인증된 `user_id`와 공구/대상 행을 서버에서 함께 검증한다.
- **승인 트랜잭션:** 공구 부모 행을 먼저 잠그고 방장, `OPEN`, 마감 전, 대상 `PENDING`, 미점유 및 빈 자리 존재를 최신 상태로 확인한다. 방장을 제외한 가장 작은 빈 `seat_no`를 점유하고 승인 순번·상태·변경 이력을 한 번에 저장한다. 중복 승인은 기존 처리 반환, 정원 초과는 상태를 변경하지 않고 거절한다. `FULL`과 잔여석은 저장하지 않고 현재 점유/빈 좌석에서 구한다. 정원 도달은 마감이 아니다.
- 신청·철회·제외·마감·정원 변경·확정도 같은 공구 잠금 순서(공구 → 종속 행)를 따른다. 주문 전 제외·철회는 해당 좌석을 비운다. 정원 변경은 점유 인원을 밑돌 수 없고 2~4 및 최소 배분 규칙을 다시 검증한다. 축소 시 방장 0번과 참여 확정 순을 보존하며 좌석을 새 범위로 재배치한다. 마감·변경 시각과 모집 문구는 같은 트랜잭션에서 갱신한다. DB 키/FK로 중복·공구 간 참조를 막고 좌석 수·방장 자리·범위 등 다중 행 규칙은 잠긴 트랜잭션에서 확인한다.

## 4. 공구 상태와 불변 정산 (F-14~F-16·F-18~F-19, §5·§6)

| 상태 전이 | 조건 |
| --- | --- |
| `DRAFT → OPEN` | 게시 입력 검증과 초기 좌석·이력 저장. |
| `OPEN → CLOSED`, `CLOSED → OPEN` | 방장이 승인 명단 확인 후 마감. 주문 전 재모집 가능. 결원이 있으면 재모집하거나 목표 인원을 실제 점유 인원으로 명시 변경한다(최소 2명); 빈 자리를 비용에 넣고 확정하지 않는다. |
| `CLOSED → SETTLING` | 실제 주문 입력과 정산 후보 생성. 예상 대비 변경점을 표시하고 조건이 달라지면 해당 버전의 승인 참여자 재확인을 모은다. 확정 버전 전에는 송금 안내·입금 확정을 시작하지 않는다. |
| `SETTLING → PICKUP → COMPLETED` | 확정 버전 및 상품 준비 후 공개 거점 수령 안내. 현재 유효 행 전부의 입금·실수령과 이전 행에 남은 환불/정정까지 해결해야 완료한다. 저금통 반영과 완료 전이를 한 트랜잭션으로 저장한다. |
| 주문 이후 정정 | `SETTLING`/`PICKUP`/`COMPLETED`에서 사유를 남기고 `SETTLING`으로 돌아간다. 금액·수량·명단 등 확정 조건이 달라지면 새 버전 후보와 재확인이 필요하다. 송금·수령 확인 오기만 바로잡는 경우는 이력 이벤트로 정정하고 버전을 유지한다. 어느 경우든 완료 조건을 재검사한다. |
| 게시 후 미완료 상태 `→ CANCELLED` | 품절·주문 취소 등 사유 기록, 모집과 신규 송금 종료. 원래 입금·확정 버전은 유지하고 미해결 환불은 취소 후에도 처리한다. 취소를 완료 또는 절약으로 계산하지 않는다. |

- `settlement_version` PK `(group_buy_id, version_no)`. 버전 번호는 후보 생성 때 단조 증가하며 폐기 번호를 재사용하지 않는다. `previous_confirmed_version_no`, `created_by/at`, `confirmed_by/at`, `change_reason`, `order_at`, 실제 가격 원천·배송/할인 플래그·환불 적용 전후 총액, 확인된 판매처 환불 근거, 상품명·수량·배분 단위/최소량·직접 소분 확인, 비교 기준/출처·환산 규격, 참여 인원, 공개 수령 거점·일시, `calculation_rule_version`을 스냅샷으로 둔다. 현재 분석이나 프리셋이 바뀌어도 과거 버전은 변하지 않는다.
- `settlement_line` PK `(group_buy_id, version_no, line_no)`, 해당 버전에서 `user_id` 유일. `line_no = 0`은 방장이고 이후는 확정 순; 좌석 번호가 아닌 이 순서를 P0의 잔여 배정에 사용한다. `user_id`, 역할, 승인 순번, 당시 별칭, 정산 수량·단위·부담금 고정. 행 수·유효 참여자 일치, `SUM(qty) = final_qty`, `SUM(amount) = final_total`, 최소 단위 충족을 확정 시 재검사한다.
- `settlement_confirmation` PK `(group_buy_id, version_no, user_id)`는 해당 정산 행 FK, 확인자와 `confirmed_at` 기록. 가격·수량·참여자 등 조건 수정은 후보 교체로 처리해 이전 확인을 재사용하지 않는다. 계산 입력·정산 행은 후보 생성부터 불변. 방장의 최종 확정은 공구 잠금 아래 현재 후보·필요 재확인·슬롯과 합계를 검증하고, 확정 메타데이터를 최초 한 번 기록한 뒤 `current_version_no`를 교체하고 후보 포인터를 비운다. 이후 버전·정산 행 및 기존 확인은 수정·삭제 금지. 후보 교체·포기는 이력에 남긴다.
- 주문 후 명단은 일반 승인/철회로 수정하지 않는다. 참여자 교체·제외는 사유와 변경 명단으로 정정 후보를 만들고, 신규 참여자의 본인확인 및 필요한 재확인 뒤 버전 확정과 현재 좌석·참여 상태를 같이 바꾼다. 이전 참여자의 행·입금·수령은 보존하며, 현재 행에서 빠졌어도 기수령품 처리와 미해결 환불을 정리하기 전 완료할 수 없다.

## 5. 외부 송금·수령·링크 (F-07·F-17~F-19, §5·§7)

- **금액 이력:** `cash_event`는 `event_id`, 공구/당사자 FK, 기준 정산 버전과 행 FK, `type`, `amount_krw`, `actor_id`, 실제 발생·기록 시각, `related_event_id`, 사유, 안정적인 요청 키를 기록한다. 일반 송금은 공구원→방장, 환불은 방장→공구원, 판매처 환불은 방장 계정으로 구분한다. `TRANSFER_REPORTED`는 참가자의 표시라 잔액을 바꾸지 않는다. `TRANSFER_CONFIRMED`는 방장의 실제 외부 확인으로 해당 신고에 최대 한 번 연결한다. `REFUND_CONFIRMED`(부분 환불 포함)·`MERCHANT_REFUND_CONFIRMED`는 별도 실제 사건이다. 오기 수정은 `REVERSAL`을 원 확정 이벤트에 최대 한 번 연결해 반대 효과를 기록하고, 필요하면 올바른 금액을 새 이벤트로 기록한다. 앱은 돈을 보내거나 취소하지 않는다.
- 모든 금액 변경은 공구 잠금 아래 대상·권한·현재 버전·관련 이벤트 중복을 재검사하고 적재한다. 이전 행에 대한 정정·환불은 현재 운영 화면에서만 처리하고, 옛 정산 행은 근거로 참조한다. `(group_buy_id, actor_id, command_kind, request_key)` 유일 및 원본 이벤트에 대한 확인·반전 각각의 유일성으로 재접속/중복 클릭을 처리한다. 한 송금 신고를 반복해도 새 지급으로 세지 않으며, 서로 다른 외부 거래는 각각 기록한다. 민감한 계좌번호·송금 이미지 원문은 저장하지 않는 제안이다. 시각/요청 키만으로 실제 은행 거래를 자동 식별할 수는 없다.
- **잔액:** 참여자의 공구 전체 `net_paid = 확인 입금 − 확인 환불`(유효한 반전 적용), `due = 최신 버전 부담금 − net_paid`. 제외된 참여자는 부담금 0으로 환불 정리까지 추적한다. 양의 잔액은 미입금·부분입금·추가 부담, 음의 잔액은 미환불; 신고만 한 금액은 실제 입금이 아니다. 판매처 부분 환불이 구매 원가를 바꾸면 근거를 연결한 새 버전에서 실결제액을 조정하고 P0와 동일한 배분으로 부담금을 재계산한다. 판매처 환불은 실결제액에 한 번만, 참여자에게 돌려준 금액은 각 참여자 `net_paid`에 한 번만 적용한다.
- **수령 이력:** `receipt_event`는 `event_id`, 공구/사용자·정산 행 FK, `type = RECEIVED | REVERSED`, 확인한 실제 총 수령량·단위, 행위자·발생/기록 시각, 반전 대상, 사유와 요청 키를 갖는다. 동일 요청 및 같은 수령 사실 재확인은 무효과, 오류는 원기록에 한 번 연결하는 반전과 새 기록으로 처리한다. 수령 여부는 공구×사용자의 유효 기록에서 계산한다. 정정 시 같은 사람·같은 품목/규격·동일 수량이면 기존 수령 사실을 사용할 수 있고, 다르면 실제 인도/회수 확인 없이는 완료하지 않는다. 노쇼·품절·취소·변경은 공구 이력에 사유·후속 조치를 기록한다.
- **링크:** `group_share_link`는 `token_hash` 유일, `group_buy_id`, `scope = RECRUITMENT | SETTLEMENT`, 정산 링크일 때만 `(group_buy_id, version_no)` FK, 발급자·시각·만료/폐기 시각을 저장한다. 모집 링크의 익명 조회는 모집 상태, 상품·모집 요약, 공개 거점만. 유효한 마감/취소 링크는 상태를 표시하되 신청을 차단한다. 정산 링크는 익명에게 상태/로그인 안내만, 본인확인된 참여자에게 해당 버전의 자기 행과 공개 거점을, 방장에게 본인 공구의 전체 내역을 보여준다. 예전 정산 링크는 그 버전을 읽기 전용으로 표시하고 최신 확정본 이동 동선을 제공하되, 이동할 때도 새 버전의 권한을 따로 판정한다. 제외된 사람은 과거 자기 행 및 본인 환불 안내에만 접근하는 안이다. 만료/폐기된 토큰은 데이터 없이 종료 처리한다.
- **카카오톡 기본 공유본:** 확정 버전의 총액·별칭별 수량/부담금·수령 일시·공개 거점만 넣는다. 실명·연락처·계좌·상세 주소·입금/환불 상태는 제외하고, 결제 정보나 상세 주소는 방장이 승인자에게 별도 전달한다. 외부 복사본은 회수할 수 없으므로 이전 버전 안내는 앱 링크가 담당한다.

## 6. 완료 공구별 절약 기록 (F-08, §4·§5·§8·§9)

- `saving_record` PK `(group_buy_id, user_id)`, `source_version_no`와 해당 `settlement_line` FK, `actual_qty`, `actual_net_cost_krw`, 정확한 절약값(`saved_numerator`, 양의 `saved_denominator`), `created_at`, `recomputed_at`, `eligible`을 둔다. 비교 규격과 실제 기준가가 확인된 완료 공구의 수령 행만 포함한다. `SAMPLE`, 보류 비교, 예상 금액, 연간 환산, 미확정 송금, 취소 공구는 합산하지 않는다. 기준 비용은 `실수령 환산량 × 소포장 기준가 ÷ 소포장 환산량`; 여기에서 실제 순부담금을 뺀다. 음수도 합산하고 표시에서만 반올림한다.
- 공구원의 실제 순부담금은 확인된 `net_paid`, 방장이 판매처에 결제하는 P1 모델에서 방장 부담금은 `환불 반영 구매 실결제액 − 다른 공구원의 순입금 합계`다. 완료에는 현재 참여자의 `due = 0` 및 정산 수량과 실수령의 일치, 제외된 사람의 순입금 0, 미해결 조치 없음, 확인된 판매처 환불의 현재 총액 반영이 필요하다. 승인 당시 예상 부담금이나 장부상의 목표액만으로 실제 부담금을 채우지 않는다.
- **완료/재완료 트랜잭션:** 공구 잠금 아래 현재 확정 버전·현금·수령 장부를 읽고 완료 조건을 검사한 뒤 해당 `(공구, 사용자)`를 삽입 또는 갱신한다. 이전 기록이 있으나 대상에서 제외되거나 기준가가 보류되면 `eligible = false`로 전환한다. 조회는 `COMPLETED`이고 현재 확정 버전과 일치하는 유효 행을 본인 기준으로 합산한다. 완료 후 정정 접수 또는 완료 조건을 바꾸는 유효 이력 추가와 동시에 공구를 재개해 이전 기록을 집계에서 제외한다. 확인·환불·수령 정리가 끝나면 같은 키로 새 값을 반영한다. 별도 누적 잔액에 증분을 더하지 않는다.

## 7. 단일 대용량 직접 소분 (F-20, §4·§8)

기본값은 `SEALED_PACKAGE`: 동일 규격의 밀봉 포장 수를 배분하고 개별 순량은 비교 환산에만 사용한다. `DIRECT`는 단일 대용량 용기이며 적합으로 판정된 품목에 한한다. `mode`, 포장 수·실수량/단위, 직접 소분 `suitability` 및 사유, 제품 표시사항 확인, 계량 단위 및 `allocation_step` 확인, 소분 용기 확인, `checked_by/at`을 확인 입력에 저장하고 주문 확정 버전에 복제한다. 제품·포장·규격·계량/용기 조건이 바뀌면 해당 확인을 다시 받는다. 하나라도 빠졌거나 부적합하면 밀봉 기준으로 되돌린다. 밀봉 기준으로 1개뿐이어서 목표 인원에게 최소 한 단위씩 줄 수 없으면 게시와 확정을 막는다. P0의 4L 섬유유연제 샘플이 `ml`·100ml 배분을 시연하는 것은 P1 직접 소분 승인이 아니다.

## 8. 설계 대조 (PRD §8, 실행 검증 아님)

| 점검 | 입력과 기대 결과 |
| --- | --- |
| 마지막 자리 동시 승인 | 3인 공구에서 0·1번이 찼고 A/B가 신청했다. 공구 잠금을 먼저 얻은 A가 2번을 채우고 커밋한다. B는 잠금 획득 후 빈 자리가 없음을 확인하고 `PENDING`으로 남는다. A의 승인 재전송도 자리를 늘리지 않는다. 모집 마감·축소가 잠금을 먼저 얻었으면 승인 조건을 새 상태로 재검사한다. |
| 이전 확정 링크 | 확정 v1 뒤 v2가 확정되면 v1 링크의 기준값·별칭·수령 안내는 v1 그대로다. 권한 있는 사용자는 최신 v2 안내로 이동한다. 미확정 후보는 최신 링크로 노출하지 않고, 익명은 두 링크 모두 정산 행을 볼 수 없다. 교체된 참여자는 최신 링크로 들어가도 타인의 행을 읽을 수 없다. |
| 정정 후 절약 재집계 | PRD §4 예시와 P0 산식: 30롤·17,701원·4명은 방장 9롤·5,311원, 공구원 각 7롤·4,130원. 같은 롤 규격의 6롤·7,800원이 확인되었다면 최초 절약은 방장 6,389원, 공구원 각 4,970원. 판매처 1,000원 부분 환불 후 v2 총액 16,701원은 같은 수량에 방장 5,010원, 공구원 각 3,897원. 각 공구원 233원씩 실제 환불하면 방장은 5,010원 순부담이다. 재완료 후 동일 키에서 방장 6,690원, 공구원 각 5,203원으로 **교체**되며, 재처리해도 한 공구에 한 건씩만 집계된다. |

현 ERD의 좌석 잠금·유일성은 승인으로 옮기고, 균등 금액 배분·방장 기준 절약·분석별 중복 키는 v1.1과 P0 계산 계약에 맞게 교체하는 안이다. 이 대조는 스키마 제안의 경로 점검이며, 배포 DB의 잠금·키 동작이나 운영 기능에 대한 빌드/테스트가 아니다.

## 9. 팀 승인 질문

1. **배포 DB·제약:** 어느 트랜잭션 DB를 사용할까? ERD의 MySQL 8/H2 표기는 기존 예시다. 선택 DB에서 행 잠금과 비어 있지 않은 좌석의 유일성, 복합 FK, 정확한 수치 범위, 시간대 표현을 확정할 것인가?
2. **인증·링크:** 방장 및 참여자 본인확인 수단은 무엇인가? 초대 만료·폐기, 익명 모집 요약의 공개 범위, 제외된 참여자의 과거 자기 행/환불 열람 기간을 이 안대로 할 것인가?
3. **개인정보 보관:** 원본 사진·모델 원문은 기본 비저장으로 둘 것인가? 선택적 비교 캡처를 제공할 경우 보관 주체·기간·만료·삭제 및 백업 반영 기준은 무엇인가? 초안·정산·송금/수령 이력의 운영 보관과 계정 삭제 처리도 정해야 한다.
4. **비교 출처·실적:** 운영 `USER_INPUT`의 확인일·증빙 요구 수준과 샘플 판매처/확인일·개정 관리는 어떻게 할까? 실제 값 확인 전 샘플 게시 금지, `SAMPLE` 저금통 제외, 조정 중 저금통 임시 제외를 채택할 것인가?
5. **운영 전이·정정:** 마감 전에 철회 후 재신청 허용 범위, 주문 후 명단 변경과 재확인 대상, 환불 증빙/수령 확인 책임 및 완료 후 정정 권한·기간을 이 안의 경계에 맞출 것인가?
6. **직접 소분:** 어떤 품목과 표시사항을 적합으로 볼 것인가? 허용 품목, 계량 규격, 용기 기준 및 확인 책임을 확정하기 전에는 밀봉 포장으로 제한할 것인가?
